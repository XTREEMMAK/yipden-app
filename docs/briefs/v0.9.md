# Claude Code prompt — YipDen v0.9

> Everything below is the brief.

## What we're building

YipDen is a mobile reader for the indie web. It follows *people*, not platforms:
one person publishes on their own site, on Bluesky, on YouTube, and YipDen pulls all
of it into one feed. Discovery comes from the IndieNodes webring.

Site and app share one name and one identity: **yipden.com** (or `.us`) is both the
marketing site and where the app is downloaded from. There is no separate umbrella
brand. Don't build or reference a "Stray Coyote" brand anywhere; that name is retired.

**Vocabulary: every single thing a followed feed produces (a post, a video, an
episode, a track) is a "yip," whatever its format.** Use it in UI strings, code
comments, and type/variable names where it's the natural word for "one followed item"
("12 new yips" beats "12 new items"). Don't rename the *follow* action: following a
person or a feed stays "follow"; a yip is the noun for what shows up afterward in Today.
Tab names (Today, Discover, Follow, Listen) are unaffected.

**v0.9 scope is deliberately small: no server, no accounts, no database.** Everything runs
on the device against public feeds and the ring's `ring.json`. The backend stack is already
decided (see "v2.0 backend" below) so that v0.9 is shaped to receive it, but none of it is
built in v0.9, and nothing in v0.9 may depend on it.

## Stack

- SvelteKit 2 + Svelte 5 (runes), TypeScript, strict mode
- `@sveltejs/adapter-static` for the reader app (Capacitor loads local files; the reader
  app has no server routes, ever)
- Capacitor for Android (iOS later), target Android 8+
- pnpm workspaces monorepo
- Vitest for unit tests, Playwright for the web build
- wavesurfer.js (current major) for the waveform/scrubber in Listen (see Listen below)
- No UI framework. Hand-rolled components, CSS in the component, shared tokens in one file
- No gesture or animation library: Svelte transitions, the View Transitions API and Pointer
  Events cover everything in "Motion" below
- **No AI/LLM dependencies anywhere in this product**

## Repo layout

```
apps/reader/            SvelteKit + Capacitor app (adapter-static)
packages/ring-client/   Framework-agnostic ring.json client (plain TS, zero deps)
packages/feeds/         Feed fetching, parsing and normalization (plain TS)
```

Reserved for v2.0, do not create in v0.9: `apps/api/` (the backend, including the feed
poller worker) and `packages/db/`.

`packages/ring-client` is destined to move into the existing `indienodes-ring` repo and be
consumed by other clients (the website, a future ambient-display app). It must not import
anything from SvelteKit, Svelte, or the app.

`packages/feeds` must also stay framework-agnostic and runtime-agnostic (no SvelteKit,
Svelte, Capacitor or browser-only APIs in its core), because the v2.0 poller will run the
same code on the server.

## packages/ring-client

Consumes `https://ring.indienodes.us/ring.json` (currently `"version": "1.0"`, shape:
`{ version, entries: [...] }`).

Entry fields today: `id`, `creator`, `type`, `form`, `why`, `tags[]`,
`tracks[{label, media_url}]`, `thumb_url`, `thumb_position{x,y}`, `source_url`,
`verification_token`, `joined_at`.

Fields to support additively (ring side will start emitting them):
`feeds[{type, url, verified}]`, `updated_at`, `discoverable` (default true), top-level
`generated_at`.

API:

- `fetchRing(opts)`: conditional GET with ETag/If-Modified-Since; pluggable cache and fetch
  so the Capacitor native HTTP client can be injected; returns cached-last-good on failure
- `validate(json)`: schema check; drop malformed entries individually, never throw away the
  whole ring; report what was dropped
- `normalize(entry)`: trailing slashes, resolved redirect targets, missing optionals
- Rotation: `nodeOfTheDay(ring, date)` (deterministic daily seed so every client agrees),
  `next(ring, id)`, `prev(ring, id)`, `shuffle(ring, seed)`
- Filters by `type`, `form`, `tags`
- Unknown fields are ignored, never dropped on round-trip. Additive-only contract.

Ship with a JSON Schema and tests, including a fixture of the real ring.json.

## packages/feeds

- Parse RSS 2.0, Atom and JSON Feed into one normalized `Item` type
  (`id, title, url, author, publishedAt, summary, contentHtml, media[], sourceFeedId`).
  This is the type that becomes a yip in the UI layer
- **Stable IDs.** `sourceFeedId` is derived from the feed's canonical URL (after redirects).
  `Item.id` is a deterministic hash of `sourceFeedId` plus the entry's own identifier
  (RSS `guid`, Atom `id`, JSON Feed `id`), falling back to the entry URL, then to
  title + `publishedAt`. The same yip must get the same `id` no matter which device or
  source fetched it, so items from different sources (see `FeedSource` below) dedupe cleanly.
- Discovery from one URL, in this order:
  1. `<link rel="alternate">` tags in the page head (RSS/Atom/JSON Feed)
  2. `rel="me"` links and h-card microformats → known profile→feed patterns:
     Bluesky `bsky.app/profile/<handle>/rss`, Mastodon `<instance>/@<user>.rss`,
     YouTube `youtube.com/feeds/videos.xml?channel_id=<UC…>` (resolve @handle → channel id
     from the channel page; if that fails, ask the user for the full channel URL),
     PeerTube and Discourse (`.rss`) feeds
  3. Fallback paths: `/feed`, `/feed.xml`, `/rss.xml`, `/atom.xml`, `/index.xml`
  4. Mark a profile `verified` when it links back to the site (two-way `rel="me"`)
- Record a feed's WebSub hub (`<link rel="hub">` in the feed, or the `Link: rel="hub"`
  header) when present. v0.9 doesn't use it; the v2.0 poller will.
- Return results as a list the user toggles on/off; never auto-follow everything silently
- Follow redirects and record the final canonical URL (real case:
  `neo.keyjayonline.com` 302s to `keyjay.neocities.org`; these must resolve to one person)
- Conditional GET on every refetch; respect `robots.txt`; honest User-Agent; per-host rate limit
- **Security (applies even on-device):** sanitize all feed HTML (no scripts, iframes, event
  handlers, or inline styles that can load remote content); XML parser with external entities
  disabled; cap response size and time. When a fetch proxy is added later for the web build,
  it must also block private/loopback IPs, including after redirects.

### FeedSource: where yips come from

All yip retrieval goes through a `FeedSource` interface, the same way storage goes through
`Store`. No component or store may call `fetch` on a feed directly.

- v0.9 ships one implementation: `DirectFetchSource`, which fetches each followed feed from
  the creator's host using the rules above.
- v2.0 adds `CachedSource` (reads from the shared feed cache, see "v2.0 backend") with
  `DirectFetchSource` as its fallback. Swapping sources must not touch any UI code.
- The exact shape is your call, but it must support:
  - fetching a **batch** of followed feeds in one call (a cache can answer that in one request)
  - **incremental results**: a per-feed or per-batch cursor (ETag/Last-Modified for direct
    fetch, an opaque cursor for the cache) so a source can return only what's new
  - per-feed results and errors, so one broken feed never fails the whole refresh
- Record the decision and the final interface in `DECISIONS.md`.

## apps/reader: v0.9 features

1. **Discover (the landing tab)**: the ring. Node of the day at the top, then browsable
   member cards with thumb, creator, why, tags. Shuffle, next/prev through the ring. Filters
   by type/form/tags. Must work with no input and auto-advance (this is also the seed of a
   future ambient/display mode), and must render from cache offline.
2. **Follow**: one tap on a ring member follows every feed in their `feeds` array. Plus a
   manual "paste a link" entry point that runs discovery from `packages/feeds` and shows the
   toggle list.
3. **Today**: merged reverse-chronological feed of yips from everything followed, with a
   source chip per yip (Blog / Bluesky / YouTube / Podcast). Header shows a yip count (e.g.
   "12 new yips · 4 people"). Filter pills: Everything / Posts / Watch / Listen. Pull to
   refresh; background refresh where Capacitor allows. Refresh goes through `FeedSource`
   and writes through `Store`; it never fetches feeds or touches storage directly.
4. **Listen**: audio player for yips with audio enclosures and ring `tracks[].media_url`,
   with a queue, a mini-player docked above the tab bar, and a full-screen player.
   - **Playback** runs on one shared `HTMLAudioElement` that the whole app uses. Pass that
     element to wavesurfer.js through its `media` option, so wavesurfer draws the waveform
     but never owns playback.
   - **Waveform is decoration; playback never depends on it.** Drawing a waveform means
     downloading and decoding the whole file, and creators' hosts may block that with CORS.
     So: don't fetch or decode anything until the user presses play; if decoding fails,
     fall back to a plain progress bar with no error shown; once peaks are computed, cache
     them on-device keyed by media URL + ETag and pass them back in through wavesurfer's
     `peaks` and `duration` options so a track is decoded at most once.
   - **Do not preload or auto-loop.** That media is hosted on members' own sites and we are
     spending their bandwidth. `preload="none"` on the audio element.
   - **Lock screen and background playback**: set the Media Session API (metadata, artwork,
     play/pause/seek/next/prev handlers). Reliable background playback on Android needs a
     native plugin with a foreground service; that is a native dependency, so propose one
     and ask before adding it.
5. **Storage**: follows, read state, cached yips and cached waveform peaks live on-device
   (SQLite via Capacitor, or IndexedDB on web), behind a `Store` interface with one
   on-device implementation. v2.0 adds a sync implementation behind the same interface, so no
   component may talk to SQLite/IndexedDB directly. OPML import and export for the follow
   list. No account, ever, for reading.

Out of scope for v0.9, do not build: clean reader view, forum digests, creator packs, claimed
creator pages, payments, sync, sign-in, webmentions, the shared feed cache, `CachedSource`,
WebSub subscriptions, any server.

## Motion

Motion is part of the product, not polish for later. It should feel smooth and unhurried:
everything eases in and out on one curve, and things fly in rather than appear.

- **One easing everywhere.** CSS token `--ease: cubic-bezier(0.65, 0, 0.35, 1)` (ease-in-out
  cubic) and, in JS, `cubicInOut` from `svelte/easing`. Export both from
  `src/lib/motion.ts` and never write a different curve inline.
- **Three durations**, as tokens: `--dur-s: 200ms` (chips, toggles, pressed states),
  `--dur-m: 320ms` (cards, fly-ins, sheets), `--dur-l: 420ms` (screen transitions).
- **Fly-ins**: Svelte `fly` (y: 16–24px, opacity 0 → 1) with the shared easing and `--dur-m`.
  Lists stagger by 40ms per item, and only the first 8 visible items stagger; the rest
  appear together so long feeds never feel slow.
- **Screen transitions** use the View Transitions API through SvelteKit's `onNavigate`
  (`document.startViewTransition`), styled with the same easing and `--dur-l`:
  - switching tabs slides horizontally in tab order (left tab → right tab slides left)
  - opening a detail view pushes in from the right; back reverses it
  - opening a yip into the full-screen player or reader morphs the card into the new screen
    via a shared `view-transition-name` on its image and title
  - where the View Transitions API isn't available, fall back to a plain crossfade
- **Swipes** (hand-rolled with Pointer Events, no library):
  - Today: swipe left/right between filter views (Everything / Posts / Watch / Listen);
    the pill indicator slides along with the finger
  - Discover: swipe the node card left/right for next/prev in the ring, the same rotation
    `ring-client` exposes
  - Full-screen player: swipe down to collapse into the mini-player; swipe the mini-player
    up to expand
  - Content follows the finger 1:1 during the drag. On release, it commits if the drag passed
    30% of the width (or height) or was a fast flick, and settles with the shared easing
    either way. Swipes must stay interruptible: a new touch mid-animation takes over.
  - Every swipe has a visible button equivalent (next/prev buttons, collapse chevron,
    pill taps). Swiping is a shortcut, never the only way.
- **Performance**: animate only `transform` and `opacity`. Hold 60fps on a mid-range Android
  phone. Keep `backdrop-filter` (frosted glass) to small, static surfaces like the player
  controls, never on anything that moves or scrolls.
- **Reduced motion**: under `prefers-reduced-motion: reduce`, replace every slide, fly and
  morph with a short opacity crossfade (`--dur-s`), and let swipes snap without the
  follow-the-finger drag.

## Visual design

Final visual design comes from the HTML mockups being produced separately; match them once
they land. Until then, build structure and motion against placeholder tokens in
`apps/reader/src/lib/styles/tokens.css` (color, type, radius, spacing, motion) so the
restyle only touches that file and the components' own CSS.

Direction, for the placeholders: warm and image-led. A deep terracotta/orange as the brand
color, a warm off-white ground, large rounded cards built around a creator's own image, pill
filter chips with a filled active state, circular play buttons, and a bottom tab bar. Imagery
comes from creators (`thumb_url`, feed images), never stock photos. Text over imagery always
gets a scrim or tint dark enough to pass the contrast rule below.

## Rules that don't bend

- **Reading never requires an account.** If a feature seems to need one, the feature is wrong.
- **No AI features**: no generated summaries, no ranking model, no third-party AI SDKs.
- Chronological only. No engagement ranking anywhere.
- Every yip links out to the creator's own URL. We are a reader, not a destination.
- Accessibility is not a later pass: real `<button>`/`<a>`/`<input>` elements, 44px minimum
  touch targets, labels on icon-only controls, 4.5:1 text contrast (including text on images
  and on orange), works at 390px wide, reduced motion honored.
- Public pages/discovery only for people who opted in (ring members). A paste-a-link follow is
  private to that device.

## v2.0 backend: decided, not built in v0.9

Recorded here so v0.9's interfaces fit it. Do not scaffold any of this in v0.9.

- **Where it lives**: a separate deployable, `apps/api/` (SvelteKit with `adapter-node`, or
  Hono; decide then). The reader app stays static and talks to it over HTTPS.
- **Database**: Postgres, reached only through a `DATABASE_URL` connection string, so the same
  code runs on:
  - Docker locally and self-hosted (a `docker-compose.yml` with a pinned Postgres image)
  - DigitalOcean Managed PostgreSQL (requires SSL; use its connection pool for the app)
  - Supabase, used **only as hosted Postgres**: no Supabase Auth, no supabase-js in the apps,
    no features that depend on row-level security or Supabase's APIs. If connecting through
    Supabase's transaction-mode pooler, prepared statements must be disabled in the driver.
  - Pin a Postgres major version that both DigitalOcean and Supabase offer. Use only standard
    Postgres features and extensions both hosts support.
- **No second datastore.** No Redis/Valkey or other cache server. Postgres handles storage,
  the job queue and the feed cache. Revisit only if measured load shows Postgres straining,
  and even then a cache server may only be a disposable cache that nothing depends on for
  correctness.
- **ORM and migrations**: Drizzle ORM with `postgres.js`; migrations are generated SQL files
  committed to the repo and run on deploy. The schema lives in `packages/db/`.
- **Auth**: Better Auth, with its Drizzle adapter, storing users and sessions in the same
  Postgres. Never hand-rolled auth.
  - The Capacitor app can't rely on cookies across origins: use Better Auth's bearer-token
    plugin, keep the token in secure native storage, and list the app's origins in
    `trustedOrigins`.
  - First sign-in methods: email magic link and passkeys.
  - Later, likely needing custom plugins: IndieAuth (sign in with your own domain, also
    how creators claim a page), Bluesky (AT Protocol OAuth) and Mastodon (per-instance
    client registration). Check Better Auth's current plugin list before building any of
    these.
  - Accounts exist for sync and for creators only. Reading stays account-free.

### Shared feed cache (v2.0)

Why: in v0.9 every device polls every feed it follows directly from the creator's host. As
users grow, a popular member's small site gets hit once per follower per refresh, phones do
a burst of requests on every open, and every client repeats the same discovery work. The
cache fetches each feed once and serves it to everyone.

- **It's a cache, not a content store.** Yips expire after a retention window (decide then).
  Every yip still links out to the creator's own URL. No clean reader view, no rehosting of
  media; audio and video still stream from creators' hosts.
- **Schema** (in `packages/db/`): `feeds` (canonical URL, ETag, Last-Modified, hub URL,
  last fetched, next fetch due, failure count/backoff), `yips` (keyed by the same stable
  `Item.id` as the client, with expiry), and `websub_subscriptions` (hub, topic, secret,
  lease expiry).
- **Poller**: a worker process in or beside `apps/api` that reuses `packages/feeds` for
  fetching, parsing, sanitizing, `robots.txt`, User-Agent and per-host rate limits. Jobs run
  on a Postgres-backed queue (pg-boss or Graphile Worker, using `FOR UPDATE SKIP LOCKED`),
  not a separate queue server.
- **What gets polled**: ring members' feeds always; paste-a-link feeds only when a client
  asks the cache for them. Paste-a-link follows stay private: the cache stores the feed,
  never who asked for it, and never tied to an account.
- **WebSub**: subscribe wherever a feed advertises a hub, verify intent and signatures, renew
  leases before expiry. Feeds without a hub fall back to scheduled polling with backoff.
- **Client API**: a "yips since cursor, for these feeds" endpoint. Responses carry
  ETag/`Cache-Control` so a CDN can serve repeat requests from the edge. No account required.
- **In the reader**: a `CachedSource` implementation of `FeedSource` that calls this endpoint
  and falls back to `DirectFetchSource` per feed on any error or miss. Reading must keep
  working if the backend is down or unreachable.
- **Web build fetch proxy**: the same deployable can serve the CORS proxy the web build needs,
  with the private/loopback IP blocking described under `packages/feeds`.

## How to work

1. Start with `packages/ring-client`: schema, types, tests against a real ring.json fixture.
2. Then `packages/feeds`: parsers and normalization first (including stable IDs), then
   discovery, then the `FeedSource` interface with `DirectFetchSource`, each with tests.
3. Then the app shell: tokens, `motion.ts`, tab bar, route transitions and the swipe
   primitive, so every feature is built on the motion system from the start.
4. Then features in order: Discover → Follow → Today → Listen.
5. Commit per milestone with a short message. Run typecheck, lint and tests before each commit.
6. Keep a `DECISIONS.md` logging any choice that differs from this brief, and why.
7. Keep a `ROADMAP.md` listing what's deferred to v2.0 (accounts and sync, the shared feed
   cache and poller, WebSub, `CachedSource`, the web fetch proxy), so the deferred work stays
   visible. Don't build any of it in v0.9.

Ask before: adding a dependency with native code (including the background-audio plugin),
adding any animation or gesture library, changing the ring.json contract, or adding anything
that needs a server.
